# ReverseHelper v1.0 MVP

## 问题与目标

希望把正在学习的 PE、IAT/EAT、UPX、Ghidra 和 Python 串成一个能公开展示的安全工具，而不是停留在零散的 CTF Writeup。第一版需要能够读取 Windows PE，整理结构和可疑信号，并输出适合继续人工分析的报告。

范围刻意限制为静态分析：不执行目标、不自动脱壳、不做“AI 判恶意”，也不把简单规则包装成确定结论。

## 分析路径

先建立统一数据流：

```text
MZ/PE 校验 → Header → Sections → IAT/EAT
          ↘ 原始字节 → Strings / Crypto constants
所有信号 → Packing heuristics → Explainable risk → Reports
```

地址处理保留 RVA、VA 和 RAW 三种视角。RVA 转换优先调用解析库，失败时再按节区区间计算：

```text
RAW = RVA - Section.VirtualAddress + Section.PointerToRawData
```

节区 Entropy、RWX、入口点位置和壳节名都只作为独立证据保存。这样报告能够回答“为什么触发”，而不是只给一个无法复查的分数。

## 静态假设与已验证事实

静态假设：高熵节区、RWX、入口点异常、少量导入与已知壳节名组合出现时，样本更值得优先检查；单个信号不足以证明加壳或恶意。

已验证事实：使用本地 Python 3.13 Windows 启动器作为正常 PE 进行只读集成测试，解析到 x86-64、8 个节区、92 个导入函数，未触发明显加壳信号，风险结果为 `2.5/10 LOW`。测试没有执行被分析的目标副本。

另一个有用观察是，正常 Python 启动器也会导入 `IsDebuggerPresent`、`GetProcAddress` 和 `VirtualProtect`。因此“可疑 API”必须解释成能力线索，不能直接解释成恶意行为。

## 修正过的问题

第一次终端验证在中文 Windows 控制台输出 Unicode 圆点时失败。报告已经成功生成，失败发生在最后的路径显示阶段。将终端装饰符改为 ASCII 后，GBK 控制台可以稳定输出。

UTF-16LE 提取的第一版在 ASCII 字符串紧邻宽字符串时，会把前一个 ASCII 字符误当成宽字符开头。为 UTF-16LE 匹配增加左边界条件后，单元测试确认结果恢复为预期字符串。

系统 Python 的用户级依赖目录不可写，因此项目改用本地 `.venv`。这也让安装和验证环境更容易复现。

## 仓库呈现的 AI 痕迹评估

当前实现不是只有 README 的空壳：核心分析流程、自动测试、真实 PE 只读验证和三种报告都已经实际运行。不过仓库一次性出现大量结构完整、语气统一的代码和文档，容易让读者判断为 AI 辅助比例较高。

最明显的痕迹不是某一段代码，而是整体过于整齐：模块命名高度对称、README 与多份文档覆盖面很全、免责声明重复、首个版本一次提交两千多行，同时缺少真实 CrackMe/UPX 对照实验、Ghidra 实机截图和逐步修正形成的自然提交历史。

后续不应伪造提交历史。更可信的改进路径是继续使用真实样本做可公开的对照实验，记录误报与规则调整，补 Ghidra 实机验证和截图，并让后续提交保持小而具体。这样项目会逐渐呈现作者自己的判断过程，而不只是完整的工程模板。

## 真实案例选择：PatchMe

《逆向工程核心原理》的 `PatchMe` 适合作为第一个真实案例：目标明确、体积较小，也能把 PE 初筛、字符串、导入 API、关键分支定位和字节补丁串成完整证据链。

发布时只保存自己的分析报告、必要截图、哈希、工具输出和验证结论，并链接作者维护的官方例程仓库。原始与修改后的二进制继续留在本地 `samples`，不复制到 ReverseHelper 公共仓库；目前没有依据声称例程具有允许任意再分发的开源许可证。

案例必须区分 ReverseHelper 的静态发现、Ghidra/x64dbg 的实际观察以及最终补丁验证，未运行过的步骤不能写成已经验证。

## PatchMe 第 20 章：静态还原结果

样本只做了只读静态分析，没有直接执行。ReverseHelper 先定位到 x86、ImageBase `0x400000`、入口 `0x401000`，并指出 `.text` 同时具备读、写、执行权限。导入表和资源字符串表明它是一个对话框程序；入口后的乱码以及对 `.text` 的写引用，则进一步指向运行时自解密。

Ghidra 中确认入口先调用解密桩。第一段从 `0x4010F5` 开始处理 `0x154` 字节，先后异或 `0x44` 和 `0x11`，等效密钥为 `0x55`。另一段从 `0x401007` 开始处理 `0x7F` 字节，密钥为 `0x07`。解密后，`0x401039` 对窗口过程区域计算重叠 DWORD 加和，并与 `0x31EB8DB0` 比较；失败时弹出 CRC 修改提示，成功时跳到 `0x40121E`。因此 `0x40121E` 可作为静态还原出的原始程序入口候选。

窗口过程中的 NAG 弹窗位于 `0x4011B4`。一个最小补丁方案是在运行时把这里的 `push 0x40` 改成 `jmp 0x4011C8`，同时把校验分支 `0x401068` 从条件跳转改成无条件跳转。考虑磁盘内容仍处于 XOR 状态，对应文件偏移和字节为：`0x468: 73 -> EC`，以及 `0x5B4: 3F 15 -> BE 47`。这只是根据静态解密得到的补丁候选；尚未在 x32dbg 中观察解密后的内存、也未运行修改版，因此不能记为动态验证通过。
